THE PROBLEM IS THE HANDOFF FROM INTENT TO EFFECT↓

01 / WHY NOW

The faster the agent, the more important the boundary.

Teams are giving agents access to tools that change real state. A prompt can ask for restraint; it cannot enforce a stop if the executor keeps running. Deadbolt puts a local decision in the dispatch path, where a denied action can be withheld before the tool body starts.

It is designed for the moment after an agent proposes an action and before trusted code performs it. Policy, a short-lived lease, one-shot operator approval and revocation all meet at that point.

02 / THE MECHANISM

One gate. Every protected dispatch.

01

Agent proposes

A tool call, spawn, destination or spend-bearing action.

→
02

Deadbolt decides

Trusted dispatcher checks lease, policy and operator state.

→
03

Executor acts—or stops

Only an explicit allow reaches the protected body.

ALLOW → execute nowDENY / ERROR → no protected dispatch

This is an integration boundary, not a magic network shield. The trusted executor must route every protected action through it and must not cache an earlier allow. Pause and kill affect subsequent admission; they do not cancel a tool body already running.

04 / EXECUTIVE BRIEF

Execution control belongs at the actual effect.

Picture an agent that can update customer records, move money or deploy code. If a human says “stop,” a chat message is a request. A gated dispatcher is a control: the next protected action must be admitted, and a revoked identity is denied.

Deadbolt can narrow the set of permitted tools and destinations, set caller-supplied spend caps, require a one-time human approval for classified irreversible actions, and record structured decisions. Teams choose what to protect and integrate the gate into the code that actually performs those actions.

THE BUSINESS QUESTIONWhen an agent is wrong, what can it still do before a person takes control?

05 / THE FAILURE MODES

The incidents to design for before they occur.

01

Runaway permissions

An agent with broad tool access can act beyond the task it was given. Put an explicit allow-list at the action boundary and deny off-policy calls.

02

Compounding mistakes

A bad plan can repeat across many calls. Short leases and operator pause or kill can prevent subsequent protected actions for an identity and registered descendants.

03

Cost and destination drift

Agents can keep spending or reach unplanned destinations. Trusted callers can supply spend and destination context for policy checks; Deadbolt does not measure bills or intercept traffic itself.

04

Approval theater

A prompt saying “ask first” is not an approval system. Deadbolt can require a one-shot operator grant for tools the team classifies as irreversible.

These are engineering scenarios, not claims that Deadbolt has prevented a customer incident. The protection is only as complete as the actions routed through the gate.

STABLE 2.0.0 / OPERATOR CONTROLS

Bound the run. Keep renewal separate.

A fixed run deadline

Choose an immutable deadline when issuing a run. Neither admission nor supervisor heartbeat moves it. After it passes, new dispatch is denied with deadline_exceeded. Cancellation of already running work belongs to the executor.

Deadline guide ↗

Supervisor-owned liveness

Fresh roots default to separate supervisor renewal. The idle TTL is 60 seconds. Provision a renewal-only key in a trusted supervisor, or deliberately choose activity mode. A late renewal cannot revive an expired or killed run.

Finite heartbeat helper & setup ↗

Explicit destination policy

When a destination allowlist is set, each tool needs an allowed declared host unless it has an operator-owned offline exception. The stdio proxy inspects url, uri, href, endpoint and host, recursively through objects and arrays. Conflicting recognized hosts are refused, including on offline-excepted tools. Unrecognized aliases and bare URL strings in other fields are not inspected. Pair policy with OS egress controls.

Parser convention & limits ↗
Keep the operator outside the model's tools. Pause, kill, clip, policy, spend and approval remain trusted operator actions. Kill stops subsequent routed calls for the identity and registered descendants. Tool denials use readable isError: true results with stable reasons and retry hints; malformed protocol requests still use protocol errors. Broad one-shot grants and exact-action approvals are distinct. The bundle launcher does not provision exact-action grants.

State lives outside the installation. An existing malformed or incomplete store fails closed; startup must not silently recreate authority. Same-user malicious code with write access to valid SQLite state is outside this containment boundary. Recovery requires operator verification. Before you start

Does DeadBolt need a model API key or cloud service?

The native gate and local file-effect evaluation do not require a model account, API key or hosted service. Your agent application may have its own provider requirements. The base Python client has no third-party runtime dependencies; the SDK adapter is optional.

Does installing the MCP bundle turn protection on?

With the operator configuration left blank, it exposes only read-only setup and bundle-integrity tools. It does not start or protect a downstream server. Configure a private operator JSON file with the trusted server, an explicit policy and a run identity, then verify the actual allowed and blocked effects. The bundle guide explains lease expiry and using a fresh identity for a new run.

Does it sandbox or stop the whole agent?

It gates actions routed through trusted dispatchers. It does not isolate the operating system, intercept arbitrary network traffic or cancel a tool body already running. The dispatcher, downstream server, state ownership and complete routing remain part of your trusted integration. Operator controls must stay outside model tools.

Is DeadBolt free to use in commercial applications?

DeadBolt is licensed under Apache-2.0 with no license fee. Inspect the license and included dependency notices. Your own hosting, client subscriptions and model-provider usage are separate. Listing in a catalog does not require buying an optional promotion or verification plan to download the GitHub release.

Where should I ask about integration or report a problem?

Open a GitHub issue with the version, OS, route and a minimal reproduction using dummy data. Follow the security reporting policy for sensitive reports. Keep keys, private review content and operator configuration out of public issues.
