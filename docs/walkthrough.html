02. Why an agent needs an execution boundary

Once an agent can write files, call services, or send messages, a bad decision can become a real change. Untrusted material can influence what the model proposes. OpenAI's current agent documentation recommends putting validation next to the tool that creates the side effect. OWASP's excessive agency guidance recommends minimum permissions, approval for high impact actions, and authorization of every downstream request. Those are engineering reasons to establish an execution boundary. They do not establish a universal legal requirement to install DeadBolt. Your application, contracts, and jurisdiction determine any specific obligation. DeadBolt supplies one deterministic control in a larger design. Combine it with narrow tools, real service permissions, schema validation, and operating system isolation appropriate to your environment.

03. How the boundary works

The model proposes work. Your trusted application validates the arguments and assigns the run identity and routed tool name. DeadBolt checks the current lease and policy. Your dispatcher starts the body only after an explicit allow. Every other result blocks the protected action. Operators manage policy, approval, and revocation through a separate control path. These controls should never be model tools. The dispatcher, database, operator credentials, and routing remain trusted. A caller that can skip the gate or change its store is outside this boundary. DeadBolt is not an operating system sandbox, and it does not shut down a frontier model. It refuses subsequent protected admissions. It also cannot cancel a tool body that is already running.

10. Leases and run identity

A lease belongs to an agent identity, not a vendor API key. Give each run an identity in trusted infrastructure. The default lease lifetime is sixty seconds. A live admission, including ordinary denials, refreshes the sliding lease. Silence allows it to expire. Killed or expired leases do not slide, and a protected tool wrapper must not silently renew an expired identity. Explicit ensure belongs in trusted setup, not in model control or a retry loop. Action deadlines and admission credential deadlines are fixed and do not slide. A fresh run needs deliberate trusted setup and policy. Track these three lifetimes separately. This makes it possible to stop a particular workflow without revoking a shared model key or interrupting unrelated applications.

11. Pause, clip, resume and kill

Pause temporarily blocks all protected admissions for one agent. Clip blocks a particular tool for that agent. Resume clears pause and clips, while preserving the configured policy. Kill revokes the agent and its registered descendants. Resume does not resurrect a kill. Choose pause when you need to investigate, clip when a single capability should stop, and kill when the run must remain revoked. Here a paused file callback does not run. After resume, a permitted callback writes a file. Clipping the write tool refuses another attempt. These are fresh sidecar decisions and observed callback effects. A control issued after an action has already been admitted cannot undo that action. Operators still need cancellation and recovery mechanisms in their application.

12. Set a useful blast radius

Policy limits the tool names an agent can use, the declared destination tokens it can reach, and caller reported spend. Unset lists remain open, so set narrow policies intentionally. A tool outside the list is refused with purpose exceeded. A foreign host is also refused. With a destination list, a network class tool missing its host is refused. Local tools without a destination are treated differently. Destination tokens must be derived from the route the body really uses. DeadBolt does not enforce DNS, redirects, network sockets, or a filesystem path jail. Spending is reported by trusted infrastructure; this is not a billing meter or an atomic purchase reservation. Crossing a configured cap stops further protected admissions. Each child requires its own policy, configured in trusted setup before dispatch.

13. Legacy one-shot approval

The existing irreversible tool policy requires an operator one shot. An unapproved attempt returns needs human. The operator approves the specific agent and tool. The next admitted call consumes that approval, and another attempt needs review again. This simple mechanism is useful when the trusted application controls the effect. Its scope is the agent and tool pair. It does not bind the recipient, message text, amount, or other arguments. Do not describe this broad permission as approval of an exact message. For effects where those values matter, use the candidate exact action path. Keep review outside model control, and consume the approval only at execution. Declining a separate application review should not burn a permission before the body is eligible to run.

14. Exact-action review: approve the content

The dispatch helper later uses a copied argument snapshot for the body. It must not read different recipients or amounts from mutable state. Register a child under its parent before starting its protected work. Then explicitly configure the child's policy. Keep database and evidence paths consistent, use private state directories, and bind locally.
